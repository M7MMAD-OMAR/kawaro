# S-135 Drag UX: drop first, then choose, with the drag icon out of the way
Status: implemented locally in 6524488, lifecycle corrected and verified by S-136; the 150 ms budgets remain unmeasured

## Story
As a user, I want to drop files somewhere sensible and then see the choices, instead of trying to hit a cell while the file manager's drag icon covers the hive, so that the first and most natural gesture works on every file manager and on every compositor. The drag icon belongs to the source application and the target cannot resize it, shrink it to a cursor or move it, so the fix is the flow, not the icon: drop first and choose after, offer a shortcut plus clipboard path with no drag at all, and keep choose-during-drag as a mode for people who want it.

## Facts found while planning (code read, plus the research in the brief)
- Source owned drag icon (research given in the brief, not re-tested in this repo): GTK sets it with `GtkDragSource.set_icon`, Nautilus builds it with `get_paintable_for_drag_selection` using thumbnails and a 64 px drag surface and stacks up to four icons, Dolphin creates a `QDrag` and sets a pixmap from `createDragPixmap` at the item widget size, and Windows lets the source specify it with `IDragSourceHelper`. A drop target cannot resize it, replace it with a cursor only image, or draw above it. This is why the story changes when the hive appears, not its size.
- The current flow is choose-during-drag. `crates/ui/src/dnd.rs` starts a drop show in `Probing` on the layer path, then `Waiting` after the drag enters; cells appear on enter, `Motion` sets `Over(i)`, and only `(Over(i), Drop)` runs an action. A `Drop` in `Waiting` (not on a cell) hides the hive. The layer catcher takes the whole output; the daemon `on_drop_files` matches actions for the dragged files and keeps them pending, and a cell click or drop submits the job. On X11 the drop hive is centred (S-115) and the drag cannot report a position before it enters the hive.
- Nothing in the current flow shows the choices after the drag ends: the action is picked during the drag, under the source icon. The hive placement is the pointer position (`layout::plan_at` with the pointer, S-019) or the centre, and the source icon can sit on the first ring of cells, which is the owner report.
- The shortcut path is hold-only today: `crates/daemon/src/portal_bus.rs` maps the GlobalShortcuts `Activated` and `Deactivated` to the long press gate (`hold_signal`) with `hold_ms`, so a tap shows nothing and the session needs a drag. `Request::Drop` in `crates/core/src/ipc.rs` carries a token, an `at` position and a `hold` flag; there is no clipboard field because the files are supposed to arrive from the drag.
- The clipboard reader exists only in `crates/cli/src/clipboard.rs` and only for Wayland and X11: `wl-paste --type text/uri-list` or `xclip -selection clipboard -t text/uri-list`, parsed by `kawaro_core::uri_list::parse`. `kawaro open --from-clipboard` uses it. There is no Windows `CF_HDROP` reader and the daemon cannot read the clipboard at all.
- The config model in `crates/core/src/config.rs` has `hive_surface`, `hold_ms`, `hold_max_ms`, `portal_shortcut`, `shortcut` and `drop_key`, and no mode for the drop flow. The settings Integration card in `crates/ui/ui/shell.slint` shows only the drop shortcut keycap; `crates/ui/src/settings.rs` keeps `hold_ms` and `portal_shortcut` as hidden state.
- The public guides `docs/drop-shortcut.md` and `docs/drop-shortcut.ar.md` describe the current choose-during-drag flow and the hold shortcut, and `README.md` and `README.ar.md` point at them. None of them mentions a mode or a shortcut plus clipboard path.
- Live behaviour on GNOME, KDE and Hyprland is not tested here. The real compositor checks stay in S-082 and are not claimed by this story; the work here is pure placement, state machine, config, clipboard and headless tests.

## Acceptance criteria
- AC1 (drop-first is the default): the default flow changes to drop first. While a drag of files with at least one action is over the drop surface, the hive shows a small non-interactive drop hint (a pill or plate near the pointer, no action cells), and the drop is accepted at any point of the large surface, not only on a cell. When the drop arrives, the drop surface is hidden and closed first, then the normal action hive opens with the dropped files at the drop point, so the source drag icon is gone before the choices appear. The hint takes no keyboard, has no click or hover action of its own, never runs an action, and is gone when the drag ends. The normal hive's first frame is at most 150 ms after the drop, and the drop hint's first frame is at most 150 ms after the drag enters a surface that has an action for the files, both measured by the existing bench style.
- AC2 (drop-first on each path): on the layer path the catcher accepts the drop over the whole output, so the user can drop anywhere on the screen; the normal hive then opens at the last drag position the catcher saw, or centred when no position was seen. On the window path (GNOME, X11, Windows) the drop target is the whole drop window and the normal hive follows the existing window rules: at the pointer on X11 and Windows when the platform can give it, centred on GNOME. A drop on the hint, beside it, or on empty surface is accepted the same way. Dropping files with no action shows the existing no-action explanation and no normal hive. The original files are untouched and the output naming stays in core.
- AC3 (choose-during-drag mode): a new setting `drop_mode` (in `config.toml` under the existing setting names, values `drop-first` and `choose-during-drag`, default `drop-first`) keeps the current flow when set to `choose-during-drag`: the cells show during the drag and a drop on a cell runs that action. In that mode the hive is placed so the cells are not under the source icon: a pure placement function offsets the hive from the pointer by a token clearance (the proposal is `Tokens.space-8` = 64 px) toward the screen side with room, and when no side has room it clamps and centres so the pointer is over the centre cell, which is a dead zone with no action cell. The drag icon may still cover the centre, but no action cell is under it. The placement is clamped to the screen and tested at the four corners and the centre of a 1280 x 800 output.
- AC4 (the setting is real and visible): `Config` gains the `drop_mode` field with serde kebab-case values, its default, an equality check and a save round trip; the daemon re-reads it through the existing 2 s config poll and applies it at the next show without a restart. The settings window Integration card gains one labelled choice row (Drop first / Choose while dragging, Arabic and English) with a descriptive label for screen readers, wired through `FormState` like the existing choices, and a save keeps the chosen mode. Unknown values fall back to `drop-first` and do not stop the daemon.
- AC5 (shortcut plus clipboard): the clipboard file list reading moves into one shared module used by the CLI and the daemon, with the same rules as today on Wayland and X11 and a new Windows path that reads `CF_HDROP` through the existing `windows-sys` dependency (no new crate) and decodes its UTF-16 list to `PathBuf`s with a pure decoder that is unit tested on Linux with a crafted buffer. In `drop-first` mode the shortcut press (GlobalShortcuts `Activated` on Wayland, the registered shortcut on Windows) reads the clipboard on a worker thread, and when it holds files opens the normal action hive for them at the last pointer if the platform can give it and centred otherwise, with no drag and no hold gate. When the clipboard is empty, unreadable or holds no files, the existing hold gate runs as today and one `clipboard: <reason>` line is written, not one per repeat. `Deactivated` closes only a hold hive and never closes a clipboard hive. In `choose-during-drag` mode the shortcut keeps the current hold behaviour exactly. `kawaro open --from-clipboard` keeps its behaviour and now uses the shared reader.
- AC6 (tests): a pure state machine or plan for drop-first proves the order (hint, accept anywhere, close the drop surface, then open the normal hive), proves the hint state has no cells and no keyboard, and proves a drop on empty surface, on the hint and beside it all accept. Placement tests prove the choose-during-drag clearance and the centre dead zone fallback at the corners and edges. Config and settings tests prove the default, parse, unknown value, save round trip, both language labels and the settings row. Clipboard tests prove the URI list path unchanged, the Windows `CF_HDROP` decoder for one file, several files, a path with spaces and an Arabic name, an empty list, a malformed buffer, and the shortcut handler with a fake clipboard: files give a normal hive and no drop show, empty or error gives the hold fallback and one log line. No test needs a live GNOME, KDE, X11 or Hyprland session; S-082 owns the real checks.
- AC7 (docs, changelog and gates): `docs/drop-shortcut.md` and `docs/drop-shortcut.ar.md` describe the drop-first default, the drop hint, the shortcut plus clipboard path and the optional choose-during-drag mode, with the same facts in both languages and the language switch line intact; `README.md` and `README.ar.md` update the drop paragraph and the settings sentence to match. One bilingual `CHANGELOG.md` line under Unreleased names S-135 and the three flows. `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, the tests of `kawaro-core`, `kawaro-ui`, `kawaro-daemon` and `kawaro-cli` pass in the touched scope; no new dependency and no new `Cargo.lock` package; no em dash or en dash in any changed file.

## Out of scope
Changing or resizing the source drag icon, a file manager integration for drag images, reading the file manager selection without a copy, drag out of Kawaro to other applications, a shelf window, a new window or a tray menu, changing the default shortcut or `hold_ms`, per-file manager drag behaviour, macOS, any clipboard format other than a file list, and the live GNOME, KDE and Hyprland checks, which stay in S-082. The portal and tray test isolation gap seen by the e2e run is a separate test issue, not this story.
