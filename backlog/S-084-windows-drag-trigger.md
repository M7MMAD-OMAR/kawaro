# S-084 Windows drag trigger without the Explorer drag modifiers
Status: approved under manager delegation (2026-10-26); the default is named only after the measurements below (S-075 rule)

## Story
As a Windows user, I want one key or one button that opens the hive while I drag a document, and it must never change what Explorer does with my drag, so that no drag silently creates a shortcut, copies or moves my file.

## Research (2026-10-26)
Explorer reserves the drag modifiers while a drag is in progress: Ctrl copies, Shift moves, Alt creates a shortcut, and Ctrl+Shift also creates a shortcut. Any held chord containing one of them flips the drag badge ("Copy to", "Move to", "Create link in") and changes what a drop outside the hive does. This is the owner's report: holding Alt to drag created file shortcuts in the system. On Windows the hive comes from the S-048 chord shortcut (default Ctrl+Alt+H) pressed during a drag, so a bare Alt hold shows nothing of Kawaro and is pure Explorer behavior.

`RegisterHotKey` needs at least one modifier and offers only Ctrl, Shift, Alt and Win. Every chord that avoids the three drag modifiers must therefore use the Windows key, and Win chords are crowded by the shell (Win+H dictation, Win+Z snap layouts, Win+C chat), while pressing and releasing Win opens Start.

The only native one-button drag Explorer leaves alone is the right-button drag: its "Copy here / Move here / Create shortcuts here" menu is the shell folder's own drop behavior and does not appear over an outside drop target such as the hive window. The leading candidate is therefore the right-button drag, the second is the tray icon as a hover drop target, and the fallback is a Win chord.

## Measurements before any implementation (a real Windows machine or the S-044 VM)
- M1: right-button drag over the hive: OLE `DragOver` and `Drop` arrive with `MK_RBUTTON`, the hive appears within 150 ms and 9 frames of the drag start, dropping on a cell runs the action and the original file stays untouched.
- M2: the same with swapped primary buttons and at 150% display scaling.
- M3: hovering the tray icon while dragging shows the hive at the pointer within 150 ms and the drop works.
- M4: Win chord candidates: whether the held chord changes the Explorer drag badge, whether Win release opens Start after the drop, and which Win+letter combinations `RegisterHotKey` can take without breaking a shell binding the machine shows in use.
- M5: the current chord (Ctrl+Alt+H) recorded for comparison: the badge state during the drag and what a drop on a folder does.

## Manager decision (2026-10-27)

- D3 (names the Windows trigger; amends AC1): the Windows drag trigger is the right-button drag, the secondary button drag whose own menu is the shell folder's "Copy here / Move here / Create shortcuts here" behavior. It is one button, it opens the hive while a document is dragged, and it never changes what Explorer does with the drag because no Ctrl, Shift or Alt is held while the drag is in progress and the shell menu does not appear over the hive. This decision line is the only place that names the trigger as shipped; user docs describe it in plain words and no UI string names a Windows trigger key. Provenance and its limit: the choice rests on the measured Explorer constraints in `references/windows-platform-facts.md`, the S-084 research of 2026-10-26, and the owner's real-machine report of 2026-10-26 that a held Alt drag created file shortcuts. The M1 to M5 live runs were not executable from this chain (no real Windows machine and no S-044 VM is reachable; S-079 owns that gap), so by manager direction of 2026-10-27 the proof boundary of this chain is unit and integration tests plus the Windows cross-check, `spikes/windows-drag-trigger/out/report.md` records M1 to M5 with the evidence on record and the pending live runs, and no measurement number is invented anywhere. The live runs stay owner-run and never become a silent code claim.
- D4 (amends the AC2 proof clause): the claim that the trigger never changes Explorer's drag is published only for triggers that hold none of Ctrl, Shift and Alt while the drag is in progress, that is the right-button drag and the tray hover. CI proves what it can observe: the pure logic of `drop_hive_allowed`, the trigger gate and the static checks. The live Explorer-side proof (a drop outside the hive leaves the original untouched and creates no shortcut) is owner-run and is recorded as pending in the spike report and the S-079 checklist, and published wording states the mechanism (no key held) instead of an unmeasured live result.
- D5 (amends the AC2a and AC5 chord clauses): the S-048 chord `Ctrl+Alt+H` keeps its taken-conflict behavior (`shortcut <string> unavailable`, daemon alive) and stays functional, but it is an undocumented internal path: it is never the documented trigger and every mention of it in user docs carries a plain bilingual warning that holding it during a drag changes what Explorer does with the drag (it holds Ctrl and Alt). The manager decision of AC1 therefore takes the warning route of AC5 and does not re-base the chord, since M4 is not measured.
- D6 (implements D1 and D2 where code exists today): this story ships the `drop_key` config key, the read-time resolution of D1 (a missing key and a stored Alt both resolve to the D3 trigger on Windows, no migration write; a missing key stays Alt where Alt was measured), the D1 capture refusal rules and their bilingual refusal texts as pure logic in `kawaro-core`. The S-076b picker consumes exactly that logic and its tests assert the same semantics; the picker window itself is not built in this story and remains S-076b scope. "Reset to the Windows default" on Windows clears `drop_key`, so the resolution returns the D3 trigger, and a custom Windows `shortcut` survives every save (AC6).
- D7 (scopes AC3's tray variant): `Source::Tray` ships in the API with its hover semantics and its tests, as AC3 states. The tray hover wiring is one part of this story, S-084c, and it waits for the M3 live measurement before it ships; until then the shipped triggers are the right-button drag and the menu.
- D8 (fixes the trigger moment in the spike report, as AC3 asks): the right-button drag triggers at the drag start, that is the secondary button held and the pointer moved past the system drag threshold (`SM_CXDRAG`, `SM_CYDRAG`) from the press point; a momentary press or movement under the threshold never shows the hive; there is no hold threshold and the S-021 real-drag rule is the gate. The key-hold trigger reuses the S-019e gate with `hold_ms`; the tray trigger is the hover.
