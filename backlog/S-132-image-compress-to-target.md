# S-132 image.compress-to: reach a byte target by downscaling when quality alone cannot
Status: in progress (this block, 2026-11-04; found by the real e2e run of 2026-11-04)

## Story
As a user, I want to ask for a picture under a size in bytes and actually get one, so that I can attach or upload it without guessing dimensions myself. Today `image.compress-to` only lowers JPEG, WebP or AVIF quality. On an ordinary 2400 x 1600 photo the engine's quality 1 is 106,428 bytes, larger than the 68,625 byte source, so a 50,000 byte target fails and writes nothing. The real e2e run recorded ImageMagick quality 1 at 23,435 bytes and PIL at 61,324, so the quality ladder alone is the limit, not the format.

## Facts found while planning (code read, plus the e2e report)
- `crates/engines/src/image.rs` `encode_to_target` tries quality 100, then quality 1, then a binary search over 2 to 99, with at most `TARGET_ENCODES` = 6 encodes per image. When quality 1 is still over the target it returns `EngineError::Failed("cannot reach {target} bytes: even quality 1 is {n} bytes")` and writes no file. There is no dimension change.
- The image encoder is the pure Rust `image` crate with its JPEG encoder (no chroma subsampling or Huffman optimisation tuning exposed). The action is `image.compress-to` in `actions/images.toml`: op `compress-to`, `ring = 2`, `order = 130`, `skip_ext = ["png"]`, output suffix `-small`, params `target_bytes = 500000` and `keep_metadata = false`, options `target_bytes` 1 to 20,000,000 (default 500,000, unit bytes) and `keep_metadata`.
- The e2e report records: source `photo1.jpg` 2400 x 1600, 68,625 bytes; `kawaro run image.compress-to --set target_bytes=50000 photo1.jpg` exits 1 with the quality 1 message and no output; `target_bytes=120000` succeeds with 117,491 bytes; ImageMagick `-quality 1` gives 23,435 bytes; PIL quality 1 gives 61,324. The report and its evidence files are under `/home/sbarah/kawaro-e2e`.
- A new encoder would add a dependency (mozjpeg, jpeg-decoder scaled decode, oxipng and similar) and would need a licence line in `docs/engines.md` and an ADR before code. The owner preferred a deterministic downscale fallback, which adds no dependency and fits the existing pure Rust engine.
- Surfaces that can show a result: the CLI prints each output path from `queue::run_job`; the daemon's end-of-job notification is built from `JobEvent` in `crates/daemon/src/jobs.rs`; MCP builds its text and `structuredContent.outputs` in `crates/mcp/src/tools.rs` with path and bytes; the stage 2 panel closes when Run submits the job, so its readout is a pre-run preview, not a result line. A result detail therefore needs one shared carrier from the engine to those surfaces.

## Acceptance criteria
- AC1 (deterministic downscale fallback): when the quality search at the current size cannot reach `target_bytes`, the engine shrinks both dimensions by the fixed step 4/5 (0.8, rounded half up, at least 1 px), keeps the aspect ratio, re-encodes and repeats the full quality search. It stops at the first size whose best encode is at or under the target. The step, the minimum side 64 px and the maximum of 16 downscale rounds are constants in the engine, never a loop without a bound. Enlarging never happens, and a source already at the minimum side is not shrunk further.
- AC2 (target, tolerance and honest failure): a successful `compress-to` writes a file whose length is at most `target_bytes` and, where quality allows, the highest quality that fits. If the target is still unreachable at the minimum size, the task fails with `EngineError::Failed` whose message names the minimum dimensions reached, the smallest bytes achieved and the target, writes no output file and leaves no temp file. A target of 0 or above 20,000,000 keeps the existing `BadParam` named `target_bytes`.
- AC3 (readout and surfaces): the final dimensions and bytes reach the user through one structured result detail, not a preformatted string, so each surface can localize it. Core gains `TaskDetail { width: u32, height: u32, source_width: u32, source_height: u32, bytes: u64, downscaled: bool }`; the `Engine` trait gains a default `fn result_detail(&self, task: &Task) -> Option<TaskDetail> { None }`; `JobEvent::TaskDone` gains `detail: Option<TaskDetail>` (serde default, skip when none) filled by the queue from that method. The CLI prints each output path followed by `WIDTH x HEIGHT, BYTES bytes (downscaled from SW x SH)` in the CLI's English; the daemon end-of-job notification body renders the same numbers in the window language, with a localized "downscaled from" phrase; MCP adds `width`, `height`, `source_width`, `source_height` and `downscaled` to each `structuredContent.outputs` entry and names the final dimensions and bytes in the result text, English like the rest of the MCP surface; the tray tooltip keeps its count and the stage 2 panel keeps its pre-run preview. A surface without the detail falls back to the existing path-and-bytes line, never to an invented size.
- AC4 (safety): the input bytes are unchanged, the only output is the final path from the core naming, a repeated run takes the next free name and never overwrites, and a cancelled or failed run leaves no output. `keep_metadata = true` still copies the JPEG APP1 and APP2 segments into the final downscaled output. The output decodes with the `image` crate and its aspect ratio is within 1 px of the source after integer rounding.
- AC5 (tests): a synthetic deterministic photo fixture (for example a noisy 2400 x 1600 PNG or JPEG generated in the test) reproduces the e2e case: a 50,000 byte target succeeds, the output is at most 50,000 bytes, both dimensions are smaller than 2400 x 1600, the aspect ratio is within 1 px, the output decodes and the input bytes are unchanged. The same fixture and target produce the same dimensions and bytes twice. A target that needs at least two downscale rounds is covered, a target below the minimum achievable size fails with the AC2 message and no output, a target that fits at the original size does not downscale, and `keep_metadata = true` survives a fallback. Surface tests: the CLI line, the daemon notification in both languages and the MCP text and output fields each carry the dimensions and bytes.
- AC6 (gates, schema and changelog): the action and option schema do not change, so the existing `image.compress-to` schema, the MCP tool list and the 17 option actions stay as they are. No new dependency and no `Cargo.lock` package, no ADR because the fallback adds no dependency and no new engine id. `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, the tests of `kawaro-core`, `kawaro-engines`, `kawaro-daemon`, `kawaro-cli` and `kawaro-mcp` pass in the touched scope, and one bilingual `CHANGELOG.md` line names S-132 and the downscale fallback. No em dash or en dash in any changed file.

## Out of scope
A new encoder or a new dependency (mozjpeg, libjpeg-turbo, oxipng and similar) and its ADR and licence work; changing the JPEG encoder settings in the `image` crate; target size for PNG, GIF, BMP, TIFF or ICO (the action still skips PNG and UnsupportedOp stays); per-file targets; a target size in KB or MB for the UI; sharpening or perceptual metrics after downscale; crop or other geometry combined with the target; the stage 2 panel showing a post-run result (the notification is the result surface); any change to `target_bytes` defaults or limits; a live compositor or real-photo check beyond the synthetic test and the e2e evidence.
