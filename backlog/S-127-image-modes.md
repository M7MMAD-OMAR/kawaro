# S-127 Image modes: resize box, anchored crop and a byte target
Status: done (2026-11-04)

## Story
As a user, I want to fit or fill an exact box, crop to an aspect at the edge I choose, and compress an image down to a byte size, so that the image I get matches what the place I am putting it in asks for. This is the P0 image work of `docs/research/image-editing-and-preview.md` (resize modes, crop with aspect, target size) and the shared geometry of S-118. Three ops on the pure Rust `image` engine, three actions, no new dependency.

## Facts found while planning
- The image engine (`crates/engines/src/image.rs`) has one op table, one `Op` parser with `BadParam` names, and one single-file run path: decode, apply EXIF orientation, transform, encode from the output extension, write `task.output` once. Output bytes are built in memory, so a failure or a cancel never leaves a partial file.
- `kawaro_core::image_geom` (S-118) already has `Mode::Fit`, `Mode::Fill` and `Mode::Exact` with `target(source, mode) -> Target { width, height, crop: Option<Crop> }`, plus the centred source crop that `Fill` uses. The engine's `resize` already calls it, so the preview and the file cannot disagree.
- The encoder (`crates/engines/src/image/encode.rs`) takes one `quality` byte for JPEG, WebP and AVIF, and ignores it for PNG, GIF, BMP, TIFF and ICO. WebP at quality 100 is lossless. That is the shape the byte target search uses.
- The option schema from S-117 is in the tree and S-120 carries values over IPC, so all three actions declare their fields and are usable through the CLI `--set`, MCP and the stage 2 form without new plumbing. A block with fields needs `kind = "form"` (ADR 0012 decision 6).
- After S-126 the registry has 50 built-in actions and 14 of them carry options. This story adds three actions with options, so the registry has 53 and the option count is 17.
- The tester's `crates/engines/tests/s127_image_modes.rs` was written from this contract in this block; the ACs below map to its seven tests one to one.

## Acceptance criteria
- AC1 (resize-box): the image engine gains the op `resize-box` and lists it in `capabilities()`. Its params are `width` and `height` (TOML integers, 16 to 20000) and `mode` (`fit`, `fill` or `exact`, default `fit`). The target is always `image_geom::target((w, h), Mode::Fit | Fill | Exact { width, height })`, with no second copy of the arithmetic:
  - `fit` resizes to the target size, keeping the aspect and never enlarging; a 400 x 300 source in a 200 x 200 box gives 200 x 150, and a 40 x 20 source in the same box stays 40 x 20.
  - `fill` crops the source to `Target.crop` (the centred crop from `image_geom`) and then resizes to exactly `width` x `height`; 400 x 300 in a 200 x 200 box gives 200 x 200.
  - `exact` resizes to exactly `width` x `height` and may distort the aspect; 400 x 300 in a 100 x 50 box gives 100 x 50.
  The output format comes from the output extension, so a JPEG input with a `.jpg` output stays JPEG. A missing, zero or 20001 `width` or `height`, or an unknown mode such as `stretch`, is `EngineError::BadParam` named after the field and leaves no output file.
- AC2 (crop aspect): the image engine gains the op `crop` with params `aspect`, one of `1:1`, `4:3`, `16:9`, `3:2` or `original` (default `original`), and `anchor`, one of `center`, `top`, `bottom`, `left`, `right` (default `center`). The output is the largest window with that aspect that fits inside the source, with integer rounding half up and at least one pixel per side: 400 x 300 gives 300 x 300 at `1:1`, 400 x 225 at `16:9`, 400 x 300 at `4:3`, and `original` or no params keeps 400 x 300. The largest-window arithmetic and the anchor placement live in `kawaro_core::image_geom` next to the existing `Crop`, and the engine calls it; a reviewer finds no second copy. An aspect outside the set (`5:4`) or an anchor outside the set (`middle`) is `BadParam` named after the field and leaves no output.
- AC3 (crop anchor): the anchor places the window and leaves the rest of the source out: with 400 x 300 and `16:9` (400 x 225), `top` starts at row 0, `bottom` at row 75 and `center` at row 37; with 400 x 300 and `1:1` (300 x 300), `left` starts at column 0, `right` at column 100 and `center` at column 50. A vertical gradient names the row of the first output pixel and a horizontal gradient names the column, so the test proves the anchor from pixel values, not only from dimensions.
- AC4 (compress-to): the image engine gains the op `compress-to` with the param `target_bytes` (TOML integer, 1 to 20000000). The run encodes the image in the output format at the highest quality from 1 to 100 whose bytes are at most `target_bytes`, using a binary search over the quality (the encoder is monotonic for JPEG, WebP and AVIF on the fixtures): a JPEG 800 x 600 target of 60000 gives a file at most 60000 bytes with the same 800 x 600 pixels. If quality 100 already fits, quality 100 is used. If even quality 1 is over the target, the task fails with `EngineError::Failed` and leaves no output. A PNG output, or any other target whose encoder has no quality control, is `EngineError::UnsupportedOp` whose message names the target. A `target_bytes` of 0 or 20000001 is `BadParam` named `target_bytes`, and the `image.compress-to` action has `skip_ext = ["png"]` so the hive does not offer a job the engine refuses.
- AC5 (actions): `actions/images.toml` gains exactly three actions after the 16 shipped image actions, for 19 in the file, and no shipped action changes:
  - `image.resize-to`: `engine = "image"`, `op = "resize-box"`, `ring = 2`, `order = 110`, `accepts = ["image"]`, `output = { mode = "per-file", suffix = "-resized" }` (extension stays the input's), icon `fit`, bilingual code and label, `[action.params]` `mode = "fit"`, `width = 1920`, `height = 1080`, and `[action.options]` `kind = "form"` with `width` (int, 16 to 20000, default 1920), `height` (int, 16 to 20000, default 1080) and `mode` (enum `fit`, `fill`, `exact`, default `fit`), all bilingual.
  - `image.crop`: `op = "crop"`, `ring = 2`, `order = 120`, `output = { mode = "per-file", suffix = "-crop" }`, code `en = "CROP"` with an Arabic twin, icon `resize`, bilingual label, `[action.params]` `aspect = "original"`, `anchor = "center"`, and `[action.options]` with `aspect` (enum of the five ids, default `original`) and `anchor` (enum of the five ids, default `center`), all bilingual.
  - `image.compress-to`: `op = "compress-to"`, `ring = 2`, `order = 130`, `output = { mode = "per-file", suffix = "-small" }`, code `en = "SIZE"` with an Arabic twin, icon `compress`, bilingual label, `skip_ext = ["png"]`, `[action.params]` `target_bytes = 500000`, and `[action.options]` with `target_bytes` (int, 1 to 20000000, default 500000, `unit = "bytes"`), bilingual.
  Each spec passes `OptionsSpec::validate`, every field and choice label is non empty in Arabic and English, and no label or code contains a long dash.
- AC6 (registry): `Registry::builtin()` has 53 actions and exactly 17 of them carry options: the 14 of S-126 plus `image.resize-to`, `image.crop` and `image.compress-to`. All three match an image selection through `Registry::matching` with the `image` engine available. The tester updates the S-117 count test from 50 to 53 and adds the three ids to its options list, and updates the registry count in `pdf_metadata.rs` from 50/14 to 53/17; the implementer edits no test file except the one it owns.
- AC7 (safety and progress): the input bytes are unchanged after every op, the only output is `task.output` (no temp file left next to it), a failure or a cancelled token leaves no output, progress starts at 0, never decreases and ends at 1.0, and the output of every successful op decodes with the `image` crate. No new dependency, no new `Cargo.lock` package, no network and the MSRV stays 1.85.
- AC8 (scope and gates): the change is limited to `crates/engines/src/image.rs`, `crates/core/src/image_geom.rs` (the anchored window helper), `actions/images.toml`, the new `crates/engines/tests/s127_image_modes.rs` and the two tester owned count updates. The existing image tests and the rest of `crates/engines/tests` pass unedited. `cargo fmt`, `cargo clippy -p kawaro-engines --all-targets -D warnings`, `cargo test -p kawaro-engines` and `cargo test -p kawaro-core` pass. No change to the UI, daemon, CLI, MCP, docs, `CHANGELOG.md` or Cargo files.

## Out of scope
Free-form crop with typed width and height, the four corner anchors and a crop overlay UI, crop or resize with a per-file value, EXIF or ICC aware resize, crop of animated formats (GIF and WebP use the first frame as they do today), a target size for PNG, GIF, BMP, TIFF or ICO (lossless or no quality control), a target size in KB or MB rounded for the UI, WebP lossless handling beyond quality 100, upscaling with a new filter or a model, and any new image format. The stage 2 form and the readout are S-119; this story only puts the fields in the actions. No new MCP tool or CLI subcommand, no docs, `CHANGELOG.md`, `docs/architecture.md`, `docs/engines.md` or Cargo changes.
