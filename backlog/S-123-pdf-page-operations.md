# S-123 PDF page operations and split modes
Status: done (2026-11-04)

## Story
As a user, I want to extract, delete and reorder pages of a PDF, and to split one into ranges or groups of N pages, so that the most common page jobs stop being a reason to open another tool. This is P0 item 1 of `docs/research/pdf-feature-benchmark.md` (page extract, delete, reorder, and split by ranges and every N pages), on the existing pure Rust `lopdf` engine. No new engine, no new process and no new dependency.

## Facts found while planning
- Shipped in 0.5.0: `pdf.compress` (Ghostscript preset), `pdf.merge` (lopdf, drops outlines and forms), `pdf.to-images` (Ghostscript, all pages, zipped), `pdf.rotate` (lopdf, degrees 90), `pdf.split` (lopdf, one PDF per page, zipped, copies the whole document per page). Benchmark section 1.
- An engine task writes exactly one output file, so a split still writes one stored ZIP (`docs/engines.md`): entries `page-001.pdf` and so on today. A folder output would be a core contract change.
- lopdf already gives page ids, page iteration and full document rewrites; the benchmark calls page extract, delete, reorder and split by ranges or every N "cheap on lopdf, no new process" (section 5, item P0 1).
- The whole document is held in memory (benchmark section 7). That is accepted for v1; a 500-page fixture must work, and the engine stays in the daemon.
- Every rewrite invalidates signatures and object IDs (section 7). This story only rewrites into a new file; the input is never modified. The hash and the page content of the input stay unchanged.
- S-117 (typed action options) already ships, so a page selection or order can be a declared field instead of a fixed param. S-120, in this block, gives the CLI `kawaro run --set` that reaches the same resolve; S-119 (the hive form) is still a draft, so for now the new actions are used from the CLI, the tests and the MCP path. ADR 0012 is the contract for options.
- Arabic labels and codes are needed in the action file like every other action; the benchmark asks for Arabic tolerant fixtures, but this story only moves pages, it does not extract or shape text, so the fixture check is page count, order and content bytes.
- The existing tests pin the PDF action set: `crates/engines/tests/pdf_actions.rs` expects 5 actions with exact rows, and `crates/core/tests/s117_options.rs` expects 45 built-in actions. Both counts are updated by the tester, as the contract says; the implementer edits no test.

## Acceptance criteria
- AC1 (engine ops): `PdfEngine::run` dispatches four ops, `extract-pages`, `delete-pages`, `reorder-pages` and `split`; `capabilities()` lists them with `MediaKind::Pdf`; an unknown op still gives `EngineError::UnsupportedOp`. Every op takes one input file and writes `task.output`.
- AC2 (pages grammar): one internal pure parser is shared by extract, delete and split ranges, so the grammar cannot drift between ops. It accepts `1`, `1-3`, `1,3,5`, `1-3,7` and the same strings with spaces around numbers, commas and hyphens (`" 1 - 3 , 7 "`); it is 1-based, ranges are inclusive, and it returns the page numbers in ascending order inside one comma group. It rejects, with `EngineError::BadParam` named `pages`, each of: an empty string; only commas; `0`; a negative number; `3-1`; `1-`; `-3`; `1,,2`; a trailing comma; a non digit; a page above the document page count (the reason names the page and the count); a duplicate page, including an overlap between two ranges (`1-2,2-3`) and a repeated page (`1-3,2`). The reason text names the offending token or page and never contains a long dash.
- AC3 (extract pages): `pages` selects the pages; the output is one PDF whose page count equals the selection size, in document order even when the string lists pages out of order (`3,1` on a 3-page file writes pages 1 then 3), with each page's text, MediaBox and inherited attributes preserved. A missing or empty `pages` is `BadParam` named `pages`. Progress ends at 1.0.
- AC4 (delete pages): `pages` names the pages to remove; the output keeps every other page in document order, with the same preservation as AC3. Deleting every page of the document is `BadParam` named `pages` and the reason says the result would have no pages; a missing or empty `pages` is `BadParam` too.
- AC5 (reorder pages): `order` is parsed with the same grammar and then must be a permutation of `1..=page_count`: every page exactly once, no range beyond the count. The output pages follow the order as written (`3,1-2` on 3 pages gives page 3, page 1, page 2; `1-3` is the identity), with the same preservation as AC3. A list that misses a page, repeats one or goes out of range is `BadParam` named `order`; a missing or empty `order` is `BadParam` too.
- AC6 (split modes): with no params the behaviour is unchanged (one stored ZIP entry per page, `page-001.pdf` and so on, same width rule). `every = N` (TOML integer, N >= 1) writes one PDF per group of N consecutive pages, groups in document order; N larger than the page count gives one PDF with every page. `ranges` writes one PDF per comma group, groups in the written order, pages inside a group in ascending order. ZIP entry names follow the source pages: a one-page group is `page-<n>.pdf`, a group with two or more pages is `pages-<first>-<last>.pdf`, both numbers zero padded to the existing width (at least 3, or the digits of the page count). So `ranges = "1-3,7"` gives `pages-001-003.pdf` and `page-007.pdf`, and `every = 2` on 5 pages gives `pages-001-002.pdf`, `pages-003-004.pdf`, `page-005.pdf`. Entries stay `Stored`, the ZIP is the only output file, and progress ends at 1.0. An `every` of 0, a negative or a non integer is `BadParam` named `every`; both `every` and `ranges` present in the resolved params is `BadParam` with a reason saying they are mutually exclusive; an empty `ranges` string is `BadParam` named `ranges`.
- AC7 (actions): `actions/pdf.toml` gains exactly three actions, all `engine = "pdf"`, `accepts = ["pdf"]`, `ring = 2`, `min_files = 1`, output `mode = "per-file"`, empty `ext` (the input stays PDF) and codes with Arabic and English:
  - `pdf.extract-pages`, `order = 20`, `op = "extract-pages"`, `suffix = "-pages"`, icon `pages`, code `ar = "استخراج"`, `en = "PAGES"`.
  - `pdf.delete-pages`, `order = 30`, `op = "delete-pages"`, `suffix = "-deleted"`, icon `clean`, code `ar = "حذف"`, `en = "DEL"`.
  - `pdf.reorder-pages`, `order = 40`, `op = "reorder-pages"`, `suffix = "-reordered"`, icon `pages`, code `ar = "ترتيب"`, `en = "ORDER"`.
  Each has a non empty Arabic and English label, and `[action.params]` with the selection as a placeholder for the stage 1 click: `pages = "1"` for extract and delete, `order = "1"` for reorder. Each also has `[action.options]` with `kind = "form"` and one string field named after the param (`pages` or `order`), which is what S-117 validates and S-120 can set: `type = "string"`, bilingual label, `default` equal to the placeholder, `maps_to` the param key.
  `pdf.split` keeps its action fields and gains `[action.options]` with `kind = "form"` and two fields: `every` (`type = "int"`, min 1, max 10000, default 1, `maps_to = "every"`, `clears = ["ranges"]`) and `ranges` (`type = "string"`, default "1", `maps_to = "ranges"`, `clears = ["every"]`), both bilingual. `pdf.split` gains no `[action.params]`, so a plain click still splits every page. Every spec passes `OptionsSpec::validate`, every label table has `ar` and `en`, and no label or code contains a long dash.
- AC8 (registry): `Registry::builtin()` has 48 actions; the three new ids are offered for a PDF selection by `Registry::matching` with the pure `pdf` engine available; every previously offered action is still offered, and no action outside `actions/pdf.toml` changes. The tester updates the S-117 count assertion from 45 to 48 and the `pdf_actions.rs` table from 5 to 8 rows (adding the three rows above); the Lead annotates S-117 AC10 instead of rewriting it. The implementer edits no test file.
- AC9 (input untouched, single output): after every op the input bytes are identical to before the run, the output is a complete PDF or ZIP starting with its magic bytes and loadable by lopdf or the `zip` crate, and no other file appears in the output directory. The engine writes only `task.output` and never renames or overwrites its input.
- AC10 (sizes and bad input): extract, delete and reorder are correct on 1-page, 2-page and 500-page fixtures (page count, order, page text and MediaBox); split is correct on 1-page, 2-page and 500-page inputs for every page, every 2, ranges and a single range. A non PDF input gives `EngineError::Input` with the input path, and an encrypted fixture gives `EngineError::Input` with a password reason, before any output file is written.
- AC11 (progress, cancel and gates): each op calls `progress` and checks `cancel` before doing work and between page groups, ends at 1.0 at most once, and a pre-cancelled token returns `EngineError::Cancelled` and leaves no output file. `cargo fmt --check` and `cargo clippy -p kawaro-engines --all-targets -D warnings` pass, and `cargo test -p kawaro-engines` and `cargo test -p kawaro-core` pass. No new dependency and no new `Cargo.lock` package (lopdf 0.45 and zip 9 are already dependencies), no network, MSRV 1.85. No change outside `crates/engines/src/pdf.rs`, `actions/pdf.toml` and the two tester owned test files.
- AC12 (out of scope honoured): no insert or duplicate pages, no split by size or bookmarks, no page thumbnails, no form, OCR, encryption or qpdf work appears in the diff, and the MCP `kawaro_pdf` op list and the CLI stay unchanged (the new actions are reachable by action id through `kawaro run` and `kawaro_convert`, not by a new MCP op name).

## Out of scope
Inserting pages from another file and duplicating pages (a later story). Split by file size, by bookmarks, or a user chosen output folder; a folder output would need a core contract change and an ADR. Page thumbnails and a page grid UI. Forms, OCR, redaction, encryption or password handling, metadata, N-up and booklet, crop, signatures and the qpdf engine (benchmark P1 and later; qpdf needs its own licence and ADR decision). Any change to the MCP `kawaro_pdf` op list, the CLI, the daemon, the UI or the hive form (S-119). Docs, `docs/architecture.md`, `docs/engines.md` and `CHANGELOG.md` are not changed in this block; the tester owns the two test count updates and the Lead owns the S-117 AC10 annotation.
