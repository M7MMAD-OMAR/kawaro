# S-131 The settings window: activation, Escape and one window per daemon
Status: implemented locally in 08976a1; real GNOME/KDE activation remains unverified under S-082

## Story
As a user, I want `kawaro settings` and the tray or menu entry to bring up the settings window with focus where the compositor allows it, to close it with Escape, and never to end up with two settings windows, so that changing a setting is one predictable window and not a hunt behind other windows.

## Facts found while planning (code read, no code changed)
- The daemon's settings window is the welcome window with an embedded settings page, not the standalone `SettingsWindow`: `crates/daemon/src/ui.rs` `show_settings` calls `welcome_window()` (the `WELCOME` thread-local holds the one window), opens it only when it is not visible, loads the saved settings only when `!win.settings_visible()`, sets the page and the update banner, and then has a foreground block that is `#[cfg(windows)]` only. On Linux there is no activation call at all, and `raise_welcome` is an empty function on non-Windows.
- The window language and focus are unchanged by repeats: a second request while the window is visible only applies the theme and updates the settings page, which is the reuse path that must be kept and tested. There is no counter or test that proves a second construction never happens, and the owner saw a duplicate settings window once.
- The activation machinery already exists: `crates/ui/src/lib.rs` keeps `PENDING_TOKEN` and the winit attributes hook applies `with_activation_token` to a new winit window; the hive sets it around a fresh window build and clears it afterwards so it cannot leak into the settings window. The welcome and settings window never sets it.
- `kawaro_core::ipc::Request::Settings` carries no payload, and `crates/cli/src/main.rs` sends it after `client::ensure_daemon()` with no token. The open path already reads `XDG_ACTIVATION_TOKEN` and `DESKTOP_STARTUP_ID` and puts the token on its request; settings does not.
- `crates/ui/ui/shell.slint` declares `callback escape()` and fires it from the shell key handler on Escape, but `crates/ui/ui/welcome.slint` never assigns that callback and no Rust handler exists, so Escape does nothing while a settings page is open. The standalone `SettingsWindow` in `crates/ui/src/settings.rs` does close on Escape in its own tests; it is a different window used by examples and tests, not the daemon settings path.
- One window is the current intent: `welcome_window()` returns early when the `WELCOME` slot is already `Some`, and `show_settings` hides nothing when the window is visible. The duplicate the owner saw is not covered by any test, and a rebuild path (`build` after a language or theme change) clears the slot without an explicit hide first.

## Acceptance criteria
- AC1 (the token reaches the settings window): `Request::Settings` gains an optional `token: Option<String>` with `#[serde(default, skip_serializing_if = "Option::is_none")]`, so an old client and an old daemon stay compatible. `kawaro settings` reads `XDG_ACTIVATION_TOKEN` first and then `DESKTOP_STARTUP_ID`, exactly as the open path does, and sends it on the request. A request JSON literal with and without `token` round trips, an old request without the key still parses, and the token is passed through the daemon to the window and never written to `config.toml` or to a log line.
- AC2 (activation on Wayland where possible): a pure `settings_focus_plan(session, has_token, window_visible, settings_visible) -> Plan` decides, with no window and no compositor: `OpenWithToken` when the window is hidden and a token exists, `RebuildWithToken` when the window is visible and a token exists, `Reuse` when the window is visible and no token exists, and `OpenPlain` when hidden and no token exists. The unit table covers `Wayland`, `X11`, `Windows` and `None`, with and without a token and with the window visible and hidden. On Wayland with a token, the daemon opens a new window with the token put into `PENDING_TOKEN` around the fresh UI and show, or, for a visible window, hides the old one and builds one fresh window with the token, so the compositor can activate it and exactly one window remains. On Windows the existing `foreground` call and its one repeat stay. With no token on Wayland or X11 the daemon performs no rebuild, writes exactly one line `settings focus: no activation token` per request, and claims nothing about focus. The token is cleared after the build so it never reaches another window.
- AC3 (Escape closes the settings window): `welcome.slint` assigns the shell `escape` callback and forwards it to Rust; `WelcomeWindow` gains an `escape` handler. On a settings page, Escape cancels the unsaved edits exactly as Back or Cancel does (the page returns to the Introduction and the last saved form values are restored) and then hides the window; it never saves, and it works while a text field has focus. On the Introduction, Escape hides the welcome window, as the existing dismissal does. A headless test dispatches Escape on the settings page and on a focused text field and asserts the window is hidden, the page is 0, no save callback fired, and the saved values are unchanged.
- AC4 (one settings window per daemon): a repeated settings request while the window is visible reuses the same window, raises it with the activation path of AC2, and updates the requested page or banner in place; it never constructs a second window. A rebuild hides the old window before the new one is shown, and the number of visible settings windows stays one at every step. A test seam counts welcome window constructions; a daemon test sends two settings requests with a fake window seam and asserts one construction, the second plan `Reuse`, and one visible window; a third test with a token asserts one construction, one replace, and still one visible window. The regression test is required, because the duplicate the owner saw has no test today.
- AC5 (gates, S-082 and changelog): every test above runs headless with no real GNOME, KDE, X11 or Hyprland session; the real focus and activation check on those compositors remains the separate S-082 item and may not be claimed by this story. `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, the tests of `kawaro-core`, `kawaro-ui`, `kawaro-cli` and `kawaro-daemon` pass in the touched scope; no new dependency and no em dash or en dash in any changed file. One `CHANGELOG.md` line in English and Arabic under Unreleased names S-131, the activation token, Escape and the single settings window.

## Out of scope
The standalone `SettingsWindow` used by examples and its own tests (it already opens one per process and closes on Escape); a settings page redesign or a new window; the welcome introduction; the language screen (S-130); a portal or shortcut based activation; GNOME, KDE, X11 and Hyprland live focus (S-082); window placement; notifications; any new dependency. The activation token is only used to ask the compositor, never to force focus against its policy.
