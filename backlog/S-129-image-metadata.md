# S-129 Keep JPEG metadata through the image ops
Status: done (2026-11-04)

## Story
As a user who edits a photo, I want to keep its Exif, XMP and colour profile when I convert it to JPEG, resize it, crop it or compress it, so that the camera data, the rights note and the colours do not silently disappear. Today every image op re-encodes the pixels and the `image` crate writes a fresh JPEG without the original metadata. A `keep_metadata` switch, false by default, restores the old metadata after the new pixels are written.

## Facts found while planning
- Every JPEG op in `crates/engines/src/image.rs` decodes the input, applies EXIF orientation, transforms the pixels and encodes a new file from the output extension. The `image` encoder writes a fresh JPEG, so the original APP1 and APP2 segments are lost. The only path that keeps original JPEG bytes is `to-pdf` (DCTDecode passthrough), which is not an image output.
- The loader already records the two things this story needs: the original file bytes in `Loaded.bytes`, and `Loaded.reoriented`, true when an EXIF orientation changed the pixels. The image engine is pure Rust and adds no dependency for this work.
- JPEG structure: `FF D8` (SOI), then a sequence of marker segments before `FF DA` (SOS). APP1 is `FF E1` and carries Exif or XMP; APP2 is `FF E2` and carries ICC profile chunks. Other segments (APP0 JFIF, APP14 Adobe, COM) are not metadata this story keeps.
- The option schema from S-117 is in the tree and S-120 carries values over IPC, so a bool field is enough and no new plumbing is needed. A block with fields needs `kind = "form"` (ADR 0012 decision 6).
- Only actions whose output can be JPEG are in scope: `image.to-jpg` (convert to JPEG), `image.resize-50` (resize), `image.resize-to` (resize-box), `image.compress` (compress, keeps the input format), `image.compress-to` (compress-to, JPEG when the input is JPEG) and `image.crop` (crop, keeps the input format). All six already carry options, so the option action count does not change.
- Final counts in this block: S-128 brings the registry to 56 built-in actions with 17 option actions, and this story adds a field to six of those 17, so the counts stay 56 and 17.
- The tester's `crates/engines/tests/s129_metadata.rs` covers the metadata copy, the default strip, a PNG source, a corrupt Exif payload and the six action declarations. The unit tests in `crates/engines/src/image/metadata.rs` cover the Exif orientation rewritten to 1, a damaged Exif payload skipped and the copy once rule. The segment exclusion (AC4) and the non JPEG output half of AC5 are still reviewer checks.

## Acceptance criteria
- AC1 (option): each of the six actions `image.to-jpg`, `image.resize-50`, `image.resize-to`, `image.compress`, `image.compress-to` and `image.crop` gains one `keep_metadata` field in its existing `[action.options]`: `type = "bool"`, `default = false`, `maps_to = "keep_metadata"`, a bilingual label, and no clears. Each action also adds `keep_metadata = false` to its `[action.params]`. No other action changes, every spec still passes `OptionsSpec::validate`, and the registry stays at 56 built-in actions with 17 option actions.
- AC2 (default false keeps today's result): with `keep_metadata` absent or false, the output of each op has no APP1 or APP2 segment. A JPEG with Exif, XMP and ICC sent through `image.to-jpg`, `image.resize-50`, `image.resize-to`, `image.compress`, `image.compress-to` or `image.crop` produces a valid JPEG with the expected dimensions and no metadata, exactly as before this story.
- AC3 (true copies APP1 and APP2): with `keep_metadata = true` and a JPEG input written to a JPEG output, the output carries the input's APP1 Exif segment, its APP1 XMP segment and its APP2 ICC segment byte for byte, in the same order as the input, placed immediately after the output's SOI and before any other segment the encoder writes. The pixels and dimensions are those of the op, not a passthrough. A metadata segment larger than one JPEG segment cannot exist in a valid input, so no reassembly is needed.
- AC4 (only APP1 and APP2): APP0 (JFIF), APP14 (Adobe), COM and any other marker segment in the input are not copied. An input with all of them plus Exif, XMP and ICC produces an output with exactly the three metadata segments and no COM, APP0 or APP14 segment.
- AC5 (JPEG only): the switch only acts when both the input and the output are JPEG. A PNG, WebP, AVIF, GIF, BMP, TIFF or ICO input with `keep_metadata = true` is accepted and the option does nothing; a JPEG input whose output is not JPEG (for example `image.compress` on a WebP, or `image.compress-to` when the output extension is WebP) is accepted and the option does nothing. Neither case fails and neither produces invalid metadata on a non JPEG file. A `keep_metadata` value that is not a TOML boolean is `BadParam` named `keep_metadata`, leaves no output file and is never read as false.
- AC6 (no double rotation, corrupt Exif safe): when the source had a non identity EXIF orientation, the engine already rotated the pixels upright. The copied Exif APP1 in that case has its Orientation tag rewritten to 1, so a viewer does not rotate the output again; the rest of the Exif payload, the XMP segment and the ICC segment are copied unchanged. A source with orientation 1 is copied byte for byte. A corrupt Exif payload is ignored without a panic: the task still succeeds and no broken Exif segment is copied. The output pixels are upright in every case.
- AC7 (safety and progress): the input bytes are unchanged, the only output is `task.output`, a failure or a cancelled token leaves no output, progress starts at 0, never decreases and ends at 1.0, and every output decodes with the `image` crate and has the expected segment bytes in the expected order. No new dependency, no new `Cargo.lock` package, no network, MSRV 1.85.
- AC8 (scope and gates): the change is limited to `crates/engines/src/image.rs`, `actions/images.toml` and the new `crates/engines/tests/s129_metadata.rs`; no other file changes. The existing image tests and the rest of `crates/engines/tests` pass unedited. `cargo fmt --check`, `cargo clippy -p kawaro-engines --all-targets -D warnings`, `cargo test -p kawaro-engines` and `cargo test -p kawaro-core` pass. No change to the UI, daemon, CLI, MCP, docs, `CHANGELOG.md` or Cargo files.

## Out of scope
Keeping metadata for PNG, WebP, AVIF, GIF, BMP, TIFF or ICO outputs (there is no metadata copy path there in this story), editing or stripping individual metadata fields, Exif thumbnails and maker notes beyond the segment copy, XMP sidecar files, colour management and ICC conversion, writing metadata into `to-pdf`, animated formats, per-file switches, the stage 2 form (S-119 owns the UI), MCP or CLI changes, and any docs, `CHANGELOG.md`, `docs/architecture.md`, `docs/engines.md` or Cargo change.
